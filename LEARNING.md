# MiniPay — the complete learning guide

## The one-sentence mental model

MiniPay is a **ledger with strict rules**: it records who owes whom, and every operation is designed so that
**retries, crashes, and attackers can't create or destroy money**. Almost every decision below serves that sentence.

**Key vocabulary you'll see repeatedly:**
- **Merchant** — a shop using MiniPay (you, the API user, act on behalf of one).
- **Order** — a customer's *intent* to pay ("₹500 for shoes").
- **Payment** — an actual money movement attempt against an order.
- **Refund** — returning captured money.
- **Idempotency key** — a client-chosen label ("order-123") that makes retries safe.

---

## 1. Money is integers, never floats — `Amount int64`, "minor units"

**Definition:** *Minor units* = the smallest coin of a currency. ₹1.00 → `100` paise. $1.00 → `100` cents.

**Why:** Floating-point numbers can't represent most decimals exactly (`0.1 + 0.2 = 0.30000000000000004`).
In a shop that error is invisible; in a ledger it compounds into real paise lost or created. Integers are exact.

**Analogy:** A cashier counts coins, never "0.3 of a rupee" on a calculator with a cracked display.
The database column is `BIGINT` for the same reason.

## 2. IDs are random UUIDs, generated by the app

**Definition:** *UUIDv4* = a 128-bit random identifier (`6a41589c-...`), so random that two generators will
never collide by accident.

**Why app-generated, not DB-generated:** The idempotency protocol must know the order's ID *before* inserting
(it links the key to the ID in the same transaction). If the DB generated it, we'd need an extra round-trip
mid-transaction. `payment.newID()` builds one with `crypto/rand` and stamps the version/variant bits.

**Analogy:** Numbering your own parcels before handing them to the courier, instead of waiting for the
courier's sticker — you can reference the number on your own paperwork immediately.

## 3. Idempotency — the single most important idea in the repo

**Definition:** An operation is *idempotent* if doing it twice has the same effect as doing it once.
(Like an elevator button — pressing it 5 times still brings one elevator.)

**Why it exists:** Networks fail *after* the server did the work but *before* the client heard back.
The client's only safe move is to retry — and without idempotency, "retry" means "charge twice."
This isn't theoretical: mobile networks, load-balancer timeouts, and user double-clicks all produce
duplicate requests daily.

**How MiniPay does it (all three money operations — orders, payments, refunds — share this pattern):**
1. Client sends `Idempotency-Key: order-123` plus the request body.
2. Server hashes the canonical body (SHA256 of `{amount, currency}`) — the *fingerprint* of "what was asked."
3. In one transaction: claim `(merchant, key)` with `INSERT ... ON CONFLICT DO NOTHING` → lock the key row
   (`SELECT ... FOR UPDATE`, see §5) → compare the stored hash with this request's hash:
   - Same key + same hash → return the original record (`200`, `created=false`). A retry.
   - Same key + different hash → `409 Conflict`. The client reused a label for a *different* request —
     a bug, and we refuse to guess which one it meant.
   - New key → do the work, link key→record, commit, `201`.

**Analogy:** A restaurant kitchen rail. You hang ticket #42 ("2 coffees") on the rail. If the waiter shouts
the order again (retry), the kitchen sees #42 already hanging and doesn't brew twice. If someone hangs a
*different* order on hook #42, the kitchen yells back (409) instead of guessing.

**Why the hash and not just the key?** The key alone can't distinguish "same request retried" from "key
accidentally reused." The hash is the disambiguator — like checking the ticket's contents, not just its number.

## 4. Hashing (SHA256) vs encryption — and why keys are hashed

**Definitions:** *Hashing* is one-way (data → fingerprint, irreversible). *Encryption* is two-way
(data → ciphertext → data, with a key).

**Why hashing here, twice:**
- Request hashes need only *comparison* ("is this the same request?") — one-way is perfect, and nothing
  sensitive leaks.
- API keys are stored as SHA256 hashes (`api_keys.key_hash`). If the database is stolen, attackers get
  fingerprints, not usable secrets. The raw `sk_test_...` key is shown **once** at issuance and never
  again — exactly like a password system that stores hashes, not passwords.

**Analogy:** A coat-check that keeps only a photo of your ticket stub, not the stub itself. Present the
stub → photo matches → coat returned. Steal the photo album → still no coats.

## 5. Transactions and row locks — the bank locker

**Definitions:**
- *Transaction* = a group of DB statements that succeed or fail **together** (ACID: Atomicity, Consistency,
  Isolation, Durability). MiniPay wraps every money operation in one: key claim + business write + key
  linkage all commit, or all roll back.
- `SELECT ... FOR UPDATE` = a *pessimistic row lock*: "I'm working on this row; everyone else queues behind me."

**Why:** Without the lock, two concurrent retries with the same key could both see "no order yet" and both
insert — a double charge in the millisecond gap. The lock serializes them: the second waits, then sees the
first one's linked record and replays it.

**Analogy:** A bank locker room allowing one person at a time. Two clerks processing the same withdrawal
form: the second waits outside, then sees the stamped form and doesn't pay out twice.

**The claim-then-link dance** (`INSERT key → work → UPDATE key SET order_id`): the key row must exist before
the work (so concurrent attempts converge on it) and point at the result after. The gap between those two is
where crashes strike — which is §6.

## 6. Crash recovery — the half-written receipt

**The problem:** A crash between "insert order" and "link key" leaves an *orphan*: the order exists, the key
points nowhere. The naive replay would insert a **second** order (double charge!).

**The fix, two parts:**
- *Orders:* a `UNIQUE (merchant_id, idempotency_key)` index plus `INSERT ... ON CONFLICT DO NOTHING`.
  The replay's insert collides with the orphan, so instead of duplicating, the code *adopts* the orphan
  (SELECTs it by key) and links the key. Converges to exactly one order. Covered by
  `TestCreateIdempotentAdoptsOrphan`, which fakes a crash with raw SQL.
- *Refunds:* same idea plus a `balance_reserved` flag, because refunds have *two* effects (a record + a
  balance change) and a crash can land between them. Replay logic: row exists + reserved → just link and
  return; row exists + unreserved → finish the reservation, then link. No double-reserve, no lost reserve.

**Analogy:** You're writing a receipt in two places — the cash book and the customer copy — and the lights go
out mid-way. Recovery rule: *before writing anything new, check whether your earlier writing is already on
the page.* The unique index is what makes "checking" reliable.

## 7. The atomic refund reservation — the last concert ticket

**Definition:** *Race condition* = the outcome depends on the timing of concurrent operations.

**The problem:** Two refunds of ₹400 against a ₹500 balance must not both succeed. A naive read-balance-then-write
allows both to read "500 available" before either writes.

**The fix:** One conditional `UPDATE payments SET refunded_amount += X WHERE ... AND refunded_amount <= amount - X
RETURNING id`. The database evaluates the condition and the write **atomically** — the loser's `WHERE` finds no
row and gets `ErrRefundNotAllowed` → `409`. No lock, no separate read: the row *is* the lock.

**Analogy:** Two people grabbing the last concert ticket: whoever's hand closes first gets it; the other's hand
closes on air. The `RETURNING` clause is feeling the ticket in your fist — empty hand (zero rows) means you
lost, no separate "check then grab" needed.

## 8. State machines — authorize → capture / void

**Definitions:** A *state machine* = an entity with allowed states and allowed transitions. *Authorize* = hold
funds (hotel blocking ₹5,000 on your card at check-in). *Capture* = actually take them (checkout).
*Void* = release the hold.

**Why split them:** Real money doesn't move instantly — the gap between "customer approved" and "merchant gets
paid" is where fraud checks, shipping, and cancellations live. MiniPay models it honestly:
- `POST .../payments` → `AUTHORIZED` (order `CREATED → AUTHORIZED`)
- `POST .../capture` → both `SUCCEEDED` (only now refundable)
- `POST .../void` → payment `CANCELLED`, order back to `CREATED` (payable again)

**Why capture/void need no idempotency keys:** Transitions are *naturally replay-safe* — capturing a `SUCCEEDED`
payment just returns it (`200`). The dangerous direction is blocked by state checks: capturing a void is `409`
(a void must never be silently undone), voiding a capture is `409` (moved money must go through refunds — an
audit trail — never vanish via void).

**Why a held payment can't be refunded:** Refunding moves money back; a hold hasn't moved money yet. The existing
`status='SUCCEEDED'` guard in the reservation UPDATE enforces this with zero new code — a nice example of one
invariant serving two features.

## 9. Authentication and tenant isolation — the hotel key card

**Definitions:** *Authentication* ("who are you?") via `Authorization: Bearer <key>`; the repo has no sessions or
JWTs — a random secret per merchant, looked up by hash each request, merchant ID placed in the request *context*
(Go's per-request bag of values).

**Why API keys, not passwords/JWTs:** Machine-to-machine payment APIs need revocable, unguessable, per-merchant
secrets. JWTs would need a signing service and expiry machinery — overkill here; a DB lookup per request is
simple and correct at this scale.

**Tenant isolation (the part that matters most):** Every read and write is scoped to the authenticated merchant —
orders/payments by `merchant_id`, payments additionally through a join (they carry no merchant column of their
own), and the refund reservation gained an `EXISTS` check through `orders` so merchant B's refund against
merchant A's payment finds no row (`409`). Unknown-others'-IDs read as `404` (we don't confirm or deny their
existence — an *oracle* would let attackers enumerate other tenants' records).

**Why `401` vs `404` vs `409` (status-code philosophy):** `401` = "I don't know you" (auth layer).
`404` = "nothing here *for you*" (reads, malformed IDs — a bad UUID is a client error, and it used to leak as
`500`, which wrongly paged the on-call engineer for a client typo). `409` = "I know you and the thing, but its
*state* forbids this" (double-pay, over-refund, capture-after-void). `500` = "my fault" — reserved for genuinely
unexpected failures, each logged with a request ID.

## 10. Production hardening — the shop opening to the public

- **Graceful shutdown** (`SIGINT`/`SIGTERM` → drain up to 10s): *Analogy:* a shopkeeper flipping the sign to
  CLOSED but still serving customers inside, instead of locking the door mid-transaction. Killing connections
  mid-`COMMIT` is how you manufacture the orphans from §6.
- **Liveness vs readiness** (`/healthz` vs `/readyz`): *Analogy:* a doctor's "are you alive?" vs "are you fit to
  work today?" Liveness restarts dead processes; readiness (which pings Postgres) pulls traffic during DB
  outages so users get fast failures instead of timeouts. Both are public — load balancers carry no API keys.
- **Rate limiting / token buckets** (600/min per IP, 120/min per merchant): *Analogy:* an amusement-park ride
  that seats 2 people per second but lets 30 queue at the gate (burst). `429 + Retry-After` is the "ride's full,
  come back in N seconds" sign — far kinder than collapsing. Idle buckets are swept so one-off visitors don't
  bloat memory.
- **Shared budgets in Postgres** (`rate_limits` table): *Analogy:* one nightclub, two entrance bouncers each
  with their own clicker — a group splits across doors and doubles the allowed entries. The shared table is the
  single clicker both bouncers check. Cost: one short transaction per request (fine here; Redis would be the
  faster clicker at 100× scale). The per-IP layer stays in-memory deliberately — flood protection needs
  cheapness, not exactness.
- **Structured logs + request IDs:** *Analogy:* every parcel gets a tracking number (`X-Request-ID`), and the
  depot logs machine-readable JSON (`merchant, method, path, status, latency_ms`) instead of handwritten notes.
  A client quoting their tracking number leads you to the exact log line.
- **Timeouts + `PORT`:** header/read/write/idle timeouts close slow-loris-style connections; `PORT` from the
  environment is how every host (Docker, Railway, K8s) tells an app where to listen — hardcoding it breaks deploys.
- **Strict JSON** (`DisallowUnknownFields`, 1MB cap, trailing-data rejection): silently ignoring
  `{"amout": 500}` (typo) would charge a default instead of erroring. *Analogy:* a pharmacist refusing a smudged
  prescription instead of guessing the drug.

## 11. Defense in depth — why rules live in two places

Service-layer checks (`amount > 0`, currency allowlist) give friendly `400`s; database `CHECK` constraints
(`amount > 0`, currency/status lists) are the backstop that holds even if a future code path forgets validation
or someone writes to the DB directly. Neither trusts the other — like a seatbelt *and* an airbag.

**Migrations as numbered SQL files** (`0001`–`0007`, `IF NOT EXISTS`, re-runnable) mean the schema is code-reviewed,
applied in order, and reproducible: any fresh database converges to the same shape. That's why each migration was
verified on a scratch database before touching the live one.

## 12. Testing strategy — why three layers

- **Unit tests** (no DB): pure logic — validation gates, hash determinism, UUID shape, limiter math, middleware
  behavior. Fast, and they run before any DB exists.
- **Integration tests** (skip without `DATABASE_URL`): the *guarantees* — replay returns the original, conflicts
  reject, orphans are adopted, over-refunds lose, voids release, cross-merchant reads vanish. Unique merchant
  namespaces per test so runs never collide; tests clean up after themselves.
- **End-to-end smoke** (live server + curl): the *wiring* — auth, status codes, JSON shapes, rate-limit trip
  counts, PORT behavior. Fixtures deleted afterward and verified gone, because a dirty dev database is how
  "works on my machine" starts.

## 13. One request's journey (putting it together)

`POST /v1/orders` with `Bearer sk_test_...` + `Idempotency-Key: order-123` + `{"amount":50000,"currency":"INR"}`:

1. **Mux** matches the method+pattern (else `405`/`404`).
2. **RequestID + Logging** tag it and start the clock.
3. **IP rate limit** (in-memory) → **Auth** (hash lookup; `401` or merchant in context) → **merchant rate limit**
   (Postgres; `429` or pass).
4. **Handler** parses strict JSON (`400` on smudges), demands the idempotency key.
5. **Service** validates amount/currency/key (friendly `400`s), fingerprints the body, mints a UUID.
6. **Store** runs claim → lock → hash-compare → insert-or-adopt → link in one transaction (`201`/`200`/`409`).
7. Access log line with the request ID; client gets JSON + `X-Request-ID`.

Every layer answers a different question — *where* (mux), *who* (auth), *how much/often* (limits), *what exactly*
(handler), *is it sane* (service), *exactly once* (store) — and that separation is why a bug in any one layer
can't silently move money.
